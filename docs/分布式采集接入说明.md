# 分布式采集：danmakus-core 兼容层

本文说明如何把 `danmakus-client` 的采集内核接到本中心，以及两侧各做了哪些适配。

## 1. 结论先行

采集端已改造完成，**开箱即连本中心，无需任何地址参数**：

```bash
cd danmakus-core
bun install && bun run build
bun run start -- --token "<后台创建的节点 Token>" --capacity-override 5
```

默认就连 `https://api.ovodm.top`。要连其它中心，只改环境变量：

```bash
DANMAKUS_API_ORIGINS=http://localhost:3001 bun run start -- --token "<Token>"
```

服务端可选环境变量（默认 10）：

```bash
DANMAKUS_NODE_CAPACITY=10
```

> 改造前的限制：上游客户端把账号中心地址写死在
> `danmakus-core/src/core/BackendApiFallback.ts` 的 `BACKEND_API_ORIGINS`，
> 而 `--runtime-url` 只能覆盖运行态接口，够不着账号中心
> （`core-config` / `info` / `recording`），启动时会打到 `api.danmakus.com` 并失败。
>
> 该问题已在客户端分支修复：内置节点改为可配置，读取优先级为
> `DANMAKUS_API_ORIGINS` → `import.meta.env.VITE_API_BASE` → `https://api.ovodm.top`。
> 详见第 5 节。


## 2. 为什么能做到"不改客户端"

`danmakus-core` 的设计是**协议解析与字段提取分离**：

- 它只负责把 B 站原始 JSON 解出来（`DanmakuClient.ingestLiveMessage`）
- 一条消息要取哪些字段、字段叫什么名字，由**服务端在 WS 鉴权响应里下发**
  （`extractionRules`，见 `DanmakuExtractor`）
- 提取结果按 msgpack 编码，经 Core Runtime WebSocket 上行

因此中心只要在下发规则里，把字段名写成自己的
`RecordedDanmakuEvent` 字段名，采集端传上来的 payload 就能直接映射入库，
解析逻辑完全不用动。规则定义在
`server_net/Services/Danmakus/DanmakusExtractionRules.cs`。

## 3. 中心侧新增的端点

客户端启动到上报，会命中以下几处。全部复用现有「采集节点」Token 体系
（`ingest_nodes.token_hash`，SHA256 比对，接受 `X-Node-Token` /
`Token` 头 / `?token=` 三种传法）。

| 端点 | 用途 |
| --- | --- |
| `GET /api/v2/account/core-config` | 核心配置：连接上限、`runtimeUrl`、重连与状态检查间隔 |
| `GET /api/v2/account/info` | 节点展示信息 |
| `GET /api/v2/account/recording` | 录制列表 = 后台启用自动录制的房间 |
| `POST /api/v2/streamer-status` | 批量查询主播是否在播（走中心缓存，省 B 站配额） |
| `WS /api/v2/core-runtime/ws` | 主通道：鉴权 / 上报 / 房间分配 / 状态推送 |

### WebSocket 帧协议

与 `danmakus-core/src/core/CoreWebSocketCodec.ts` 完全一致：

```
+--------+-----------------+-------------------+
| opcode | seq (uint32 LE) | msgpack payload   |
| 1 byte |     4 bytes     |  remainder        |
+--------+-----------------+-------------------+
```

| opcode | 方向 | 说明 |
| --- | --- | --- |
| `0x01` | C→S | 鉴权，`{token, clientId, version}` |
| `0x02` | C→S | 上报批次，外层 `{compression, payload}` |
| `0x03` | C→S | 状态汇报 / 心跳，`{holdingRooms, connectedRooms, capacity, ...}` |
| `0x81` | S→C | 鉴权结果，含 `extractionRules` 与 `serverTime` |
| `0x82` | S→C | 上报 ACK，`{acceptedCount, rejected[]}` |
| `0x83` | S→C | 房间分配推送 |
| `0x84` | S→C | 主播开播状态推送 |
| `0x8F` | S→C | 错误通知 |

上报体支持 **zstd / brotli / gzip / identity** 四种压缩，
服务端按信封里的 `compression` 字段反向解压
（见 `Services/Danmakus/DanmakusUploadEnvelope.cs`）。
Bun/Node 默认走 zstd。

## 4. 多节点协作

### 房间分配

`DanmakusRoomAllocator` 保证同一房间同一时刻只分给一个节点：

1. 候选 = 后台启用自动录制（`rooms.auto_record = 1`）且正在直播的房间
2. 粘性：节点已持有的房间只要还在播就继续给它
3. 补位：按持有量从少到多，把空闲房间分下去
4. 回收：下播立即收回；节点掉线后房间进入可分配池

任一台机器关掉，它负责的房间会在下一轮汇报时被其它节点接管。

### 会话归并

会话身份是 **`(主播 uid, 直播开始时间)`**，不是"某台机器的某次录制"。
开播时间取自 B 站下发的 `live_start_time`，任何节点算出来都一样，
所以：

- A 录前半段、B 录后半段 → 落到同一个 Session，前端看到一条连续时间线
- 中间换机器、重启客户端 → 仍然续写同一场

### 跨节点去重

每条消息带 B 站真实唯一 ID（`message_id`），SQLite 侧有唯一索引 +
`INSERT OR IGNORE`，多节点重复上报会被自动丢弃。

ID 来源：

| 消息 | ID 来源 |
| --- | --- |
| `DANMU_MSG` | `info[0][15].extra.id_str`（JSON 字符串内部，多数弹幕没有，走兜底） |
| `SEND_GIFT` | `data.tid` / `data.rnd` |
| `SEND_GIFT_V2` | pb 字段 9（`gift_items[].tid`） |
| `SUPER_CHAT_MESSAGE` | `data.id`（`_JPN` 同 id，天然去重） |
| `GUARD_BUY` | `guard-{uid}-{start_time}-{level}` 构造 |
| `USER_TOAST_MSG` | `toast-{uid}-{start_time}-{level}` 构造 |

**兜底算法必须两侧一致**，否则同一台机器走本机录制和走节点上报会算出不同的键：

```
fp- + SHA256("{uid}|{timestamp}|{text}") 前 12 字节（十六进制）
```

实现见 `BilibiliRecorder.BuildFallbackMessageId`，
`DanmakusEventMapper` 直接复用它。

## 5. 采集端改动清单

| `danmakus-core/src/cli/index.ts` | CLI 描述与 Token 提示改为采集节点语义 |
| `src/services/apiNodes.ts` | 去掉写死域名，节点标签按 `BACKEND_API_ORIGINS` 动态生成 |

| `src/components/core-control/CoreControlAccountTab.vue` | 同上 |

| `README.md` / `.env.example` | 重写为本中心接入说明 |

### 为什么必须改 core 层

`AccountApiClient` 的账号中心地址由 `BACKEND_PRIMARY_ORIGIN` 推导：

```ts
const DEFAULT_ACCOUNT_API_BASE = `${BACKEND_PRIMARY_ORIGIN}/api/v2/account`;
```

而 `--runtime-url` 只影响 `RuntimeEndpoints`（运行态/上传/状态接口）。
客户端 `start()` 的第一步就是 `prepareAccountConfig()` 拉 `core-config`，
地址不对会直接启动失败，连 WS 都建立不起来。

### 三端读取顺序

```ts
// 1) CLI / Docker / PM2：运行时环境变量
process.env.DANMAKUS_API_ORIGINS
// 2) Vite 前端：构建期注入
import.meta.env.VITE_API_BASE
// 3) 兜底
'https://api.ovodm.top'
```

> 踩过的坑：只读 `process.env` 不够。Vite 打包 HTML 客户端时会把
> `typeof process` 折成常量，产物里 `process.env` 变成 `{}.X`，
> 浏览器侧永远取不到值。所以必须同时支持 `import.meta.env`。

## 6. 验证方式

本地联调脚本（仓库外，仅开发用）：

1. `ws_probe.ts` —— 协议级：鉴权、规则下发、zstd 上报、ACK、房间分配
2. `e2e_probe.ts` —— 端到端：真实 `DanmakuClient` 连真实直播间，验证规则提取与入库
3. `dual_probe.ts` —— 双节点并发，验证跨节点去重

验收标准：

- 双节点同时录同一房间，中心入库条数 ≈ 单节点条数（不是两倍）
- 场次库里 `COUNT(message_id) == COUNT(DISTINCT message_id)`
- 用户名不是 `xxx***`（登录态鉴权）
- WS 断开后 `sessions.end_time` 保持 0，其它节点可继续追加

## 7. 已知限制

- **`id_str` 覆盖率**：大部分 `DANMU_MSG` 的 `extra` 里没有 `id_str`
  （B 站只对部分弹幕下发），实际约 70% 走内容指纹兜底。
  兜底键已两侧对齐，跨节点去重仍然正确，但指纹碰撞理论概率略高于真实 ID。
- **会话封盘**：采集节点没有"录制结束"事件。`SessionAutoFinalizeService`
  每 2 分钟检查一次，满足「空闲 ≥ 10 分钟 + 直播已结束」才封盘。
- **上游单元测试**：客户端有 2 项测试在改造前就不通过
  （`RuntimeConnection.backend-integration` 需要真实后端服务器，
  `DanmakuMessageQueue` 的 1 秒合并断言有计时抖动），与本次改造无关。
- **本期不做**：用户体系、采集端 GUI 深度定制、关键帧/字幕上传。

## 8. 部署顺序

1. **先部署中心**（本仓库），让 `/api/v2/*` 兼容端点上线
2. 后台「采集节点」创建节点，拿 Token
3. 再分发采集端（客户端仓库），配 Token 启动

顺序不能反：采集端启动第一步就要求 `/api/v2/account/core-config`，
中心没上线会直接启动失败。

蓝绿部署期间不受影响：`core-config` 返回的 `runtimeUrl` 取自当前请求的
`Request.Host`，客户端会自动跟随到新槽位。
